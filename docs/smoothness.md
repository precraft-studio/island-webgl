# 網站「順暢」的組成要素

這份筆記裡的每個數字都來自這個專案的實測或對 mont-fort.com bundle 的閱讀，
不是通則性的效能建議。

---

## 一、順暢不是一件事，是四件

把它們混為一談，是「幫我弄順一點」這種需求通常失敗的原因。

| | 是什麼 | 壞掉時的感覺 | 屬於哪種問題 |
|---|---|---|---|
| **幀率** | 畫面持續送出的能力 | 頓、格放 | 吞吐量 |
| **延遲** | 輸入到畫面回應的時間 | 遲鈍、黏 | 反應時間 |
| **一致性** | 各層是否對同一個手勢說同樣的話 | 說不上來的「怪」 | 設計 |
| **可預測性** | 有沒有突發的停頓 | 卡一下 | 尖峰 |

這個專案兩種問題都遇過，而且**是分開發生的**：先修好幀率（8fps → 44fps），
使用者仍然回報「還是有點延遲感」。因為那是第二和第三項。

---

## 二、幀率

### 先確定你是被什麼卡住

掃一遍解析度，把每幀時間對像素數作線性擬合。截距是解析度動不到的固定成本，
斜率是每像素成本。這個場景在 390×844、Intel UHD 630 上：

| 裝置像素比 | Mpx | GPU ms | fps |
|---|---|---|---|
| 2.0 | 1.32 | 120.6 | 8 |
| 1.0 | 0.33 | 47.9 | 21 |
| 0.6 | 0.12 | 22.9 | 44 |
| 0.5 | 0.08 | 18.4 | 54 |

擬合出 **11.8ms 固定 + 82.4ms/百萬像素**。斜率遠大於截距 → fragment-bound
→ 解析度是唯一有這種幅度的槓桿。如果反過來（截距大），砍解析度沒用，要去找
幾何、draw call 或 CPU。

### 用對量測工具

`EXT_disjoint_timer_query_webgl2` 給的是真正的 GPU 時間，而且會回報樣本是否
被打斷。用 wall clock 包 `readPixels` 量，在這台機器上同一組設定量到 96.4ms
和 63.8ms——噪音比訊號大，足以支持任何結論。

### 隔離成本

一次隱藏一個物件，看省下多少。這個場景在 dpr1：地形 30.2ms、水 16.8ms、
空盤 4.8ms。地形一個就佔一半以上。

### 裝置能力查不到，只能量

GPU 型號、當下的發熱降頻、電池模式——沒有任何一個能從 user agent 讀出來。
所以不要寫死常數，要做**回饋控制**：量幀時間，調解析度。

實作上的細節都是有代價的：

- **觸控裝置從低往上爬，不要從滿往下掉。** 從滿解析度開場的手機，前幾秒是
  8fps——那就是訪客決定「這網站壞了」之前看到的全部。
- **用中位數不用平均數。** 一次 GC 或 shader 編譯會進平均數，然後你為了一個
  跟像素無關的幀去砍解析度。
- **每次調整本身就是頓格**（重新配置 render target）。所以要有遲滯、冷卻、
  死區。我第一版在一次降頻中觸發了 14 次重配置，修好後是 2 次。
- **爬升門檻不能低於螢幕更新率。** rAF 在 60Hz 螢幕上最快就是 16.7ms。我第
  一版把門檻設在 13.6ms，那永遠達不到，控制器只會降不會升。

## 三、延遲

### 平滑必須與幀率無關

```js
x += (target - x) * 0.045;              // 錯：每幀固定比例
x += (target - x) * (1 - Math.exp(-λ * dt));   // 對：每秒固定速率
```

錯的版本，實際反應時間會隨幀率惡化：

| | 60fps | 45fps | 30fps |
|---|---|---|---|
| 每幀 0.045 | 367ms | 484ms | 726ms |
| λ = 5/秒 | 200ms | 220ms | 231ms |

**它在慢的裝置上最慢**——正好是幀率已經有問題的地方，兩個問題疊在一起。
這個 bug 在本專案存在過，而且只在指標視差上，因為另外兩處已經做了補償。

### 用「時間常數」當共同語言

`λ` 是每秒速率，走完 63% 的時間 = `1/λ`。有了這個單位，才能跨網站、跨函式庫
比較。感知上的分界大致是：

| 時間常數 | 讀起來像 |
|---|---|
| < 100ms | 跟手、綁在一起 |
| 150–250ms | 有回應，有重量 |
| 500ms | 一段刻意的動畫 |
| 1–2s | 飄移、氛圍，不像「回應」 |

## 四、一致性（最容易漏掉的一項）

**這是本專案真正的問題。**

參考網站的所有阻尼都比我們**重**：

| | 目標網站 | 我們 |
|---|---|---|
| 拖曳 → 畫面 | 1000ms | 214ms |
| 相機視差 | 2000ms | 2000ms（原本 360ms） |
| 捲動 → 相機 | 167ms | 177ms |

它拖曳的阻尼是我們的 4.7 倍，卻沒有延遲感。所以**「阻尼重 = 延遲感」是錯的。**

差別在平滑放在哪一層：

- **他們**：Lenis 平滑捲動位置本身 → DOM 文字和 3D 相機**讀同一個值**。一條曲線。
- **我們**：原生捲動（滾輪一格瞬間跳約 100px）→ DOM 用 `scrub:true` 跟著跳，
  相機再經一層阻尼滑過去。**同一個手勢，兩條曲線。**

文字瞬間到位、世界還在追。大腦把這個落差讀成延遲，即使沒有任何一層是慢的。

> **規則：平滑「來源值」一次，讓所有消費端讀它。不要每個消費端各自平滑。**

還有一個相關的細節：他們拖曳時，`pos` 是**跟手指 1:1 立即更新**的，只有拿去
算畫面的 `lerpedPos` 在後面追。**系統狀態即時，視覺才平滑**——這跟「延遲輸入」
是兩回事。

## 五、量測紀律

這個專案有兩個我「很有把握」的推論被實測推翻：

| 推論 | 實際 |
|---|---|
| hash 裡的 `sin` 每像素上千次，一定是元兇 | 換掉之後**慢了 15%**——超越函數有專用單元，本來閒著 |
| bloom 有多重 mip 模糊，一定很貴 | **0.38ms** |

另外一次是讀錯來源：我把相機視差對到了目標網站的**游標裝飾**常數（200ms），
而不是它的**相機**常數（2000ms），差 10 倍。

> 講得有多肯定，跟它有多正確，沒有關係。動手前先量。

### 模擬你手上沒有的裝置

把控制律寫成 `(狀態, 幀時間) → 新狀態` 的**純函式**，就能對著成本模型跑一台
你沒有的手機——包含中途降頻。這個專案就是這樣驗證解析度控制器的，因為朋友的
手機不在手上。

## 六、會靜默失敗的東西（要用機器檢查，不要靠記憶）

這些在本專案全都發生過，**而且完全沒有 console 錯誤**：

- template literal 裡的註解出現反引號 → 整個 import graph 掛掉，頁面停在 loader
- GLSL 保留字當變數名（`patch`）→ 該 shader 不編譯，物件不畫，但沒有任何訊息
- uniform 宣告了卻沒綁定（`sampler2D`）→ 水面提交了 96,800 個三角形，畫成全黑
- `getElapsedTime()` 內部會再呼叫一次 `getDelta()` → 下一幀的 delta 短少，
  所有阻尼和效能控制器都被影響

---

## 七、檢查清單

1. 是幀率問題還是延遲問題？先分清楚，它們的解法沒有交集。
2. 掃解析度、擬合直線 → 確認是不是 fragment-bound。
3. 用 timer query，不要用 wall clock。
4. 所有平滑改成 `1 - exp(-λ·dt)`。
5. 把每個係數換算成「走完 63% 的毫秒數」，列出來看。
6. 找出誰在讀同一個手勢 —— 他們拿到的是同一個值嗎？
7. 裝置能力用回饋控制，不要寫死；調整本身要有遲滯。
8. 靜默失敗用建置期檢查擋住。
